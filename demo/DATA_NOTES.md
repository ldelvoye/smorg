# Demo data notes

`linear_data.py` and `github_data.py` feed the recorded terminal demo (`demo/harness.py`, `demo/run.py`). Everything in them is invented: a fictional developer-tools company, Palisade Labs, building a job scheduler called Ferry. No real companies, tickets, repositories, or people appear anywhere in either file.

## linear_data.py

**Cast:** the viewer is Dana Okafor (`Viewer`, first in `ITEMS`). Nine other invented engineers (Marcus Webb, Priya Nair, Tomasz Kaczmarek, Yuki Tanaka, Naomi Reyes, Felix Brandt, Elena Kowalski, Sam Whitfield, Grace Liu) fill out assignees, creators, and commenters.

**Top-level issues (16 `Issue` items).** Spread across the four statuses the issue list groups by: 5 In Progress, 4 In Review, 4 Todo, 3 Blocked, so `LinearIssues`'s status-group cards (`views/issues.py`) all render. Priorities cover all five values Linear's own icon set draws (`glyphs.format_priority`): Urgent (3), High (3), Medium (4), Low (4), No priority (2). Two titles (`RUN-501`, `RUN-506`) run well past 130 characters specifically to overflow a 120-column terminal and exercise the selected row's marquee scroll (`marquee_window` in `views/issues.py`). `updated_at` values are spread from 2 hours to 5 days before `NOW`, all in the past.

**Projects (4 `Project` items).** `PROJECT_BACKPRESSURE` ("Queue backpressure rework") is the started showcase project, with three milestones at 100/55/0 percent progress to exercise `format_progress_bar`'s different fill levels. `PROJECT_CLI_V2` ("Ferry CLI v2 rewrite") is planned, `PROJECT_WEBHOOK_RETIREMENT` ("Legacy webhook relay retirement") is completed, `PROJECT_WORKER_AUTOSCALING` ("Worker pool autoscaling") is a second, smaller started project. Together they exercise every branch of `project_glyph`/`status_color` and the projects list's status grouping (`views/projects.py`).

**Issue detail pages (`IssueDetail`, 33 entries).** Three issues (`RUN-501`, `RUN-506`, `DAT-301`) are fully "rich": multi-paragraph markdown descriptions with a bulleted list and a code span, labels, a due date, an estimate, and 1-3 comments, exercising `LinearIssueView`'s description card, labels section, properties (estimate/due date glyphs), and activity card. `RUN-501` additionally carries a parent (`ParentSummary`), two sub-issues, and one entry each in `blocked_by`/`blocks`/`related`, so the issue page's "open from here" picker (`action_open_from_here`) has every section populated. Every id it references (`RUN-500`, `RUN-508`, `RUN-509`, `DAT-304`, `RUN-510`, `GRW-403`) has its own `DETAILS` entry so opening it from the picker works. The remaining 13 top-level issues and the project-tree-only issues get a lighter but still real `IssueDetail` (one-line description, a creation transition, 0-1 comments) via the `_light_detail` helper, so opening any issue in the demo never crashes.

**Project issue tree (`ProjectDetail.issues`).** `PROJECT_BACKPRESSURE`'s detail carries 17 `ProjectIssue` entries: three in-flight roots (`RUN-501`, `RUN-506`, `RUN-517`), whose subtrees reach 4 levels deep (`RUN-501` -> `RUN-502` -> `RUN-512` -> `RUN-513`) to exercise `LinearProjectIssues`'s tree indentation (`views/project_issues.py`), plus 4 standalone issues (2 backlog, 1 completed, 1 triage) that only ever show up in the status tally line, never as a selectable row. Assignees mix the viewer's own name ("Dana Okafor", on about half the tree) with other engineers and a few unassigned rows, exercising `_format_assignee`'s three branches (mine / someone else's first name / blank). The other three projects get smaller, single-level issue lists (root issues reused from the top-level list where their `project` field already ties them in, plus a couple of backlog/done rows) since only the started showcase project needed the 15-25/three-levels-deep tree.

## github_data.py

**Profile.** `PROFILE` (login `dokafor`) carries a full 53-week contribution calendar generated by a small seeded `random.Random`, weighted so weekdays are busier than weekends, so `GitHubMenu`'s contribution graph (`_format_graph_rows`, month header) has a full year to lay out.

**Pull requests (10 `PullRequest` items).** One or two per `Category` value (`NEEDS_YOUR_REVIEW` x2, `NEEDS_TEAM_REVIEW` x1, `DRAFT` x2, `WAITING` x2, `NEEDS_ACTION` x1, `READY_TO_MERGE` x2), so both of `GitHubInbox`'s bands ("review inbox" / "your pull requests") show every section card. `updated_at` is spread from 2 hours to 2 days before `NOW`.

**Pull request details (`PullRequestDetail`, all 10).** Reviewer states cover all five `ReviewerState` values across the set (requested, approved, changes requested, left comments, dismissed), exercising every branch of `_reviewer_sign` in `views/pull_request.py`. Two drafts (`PR_450`, `PR_470`) use `UNAVAILABLE_CHECKS` to exercise the "no checks" line. `PR_421` has failing checks with named failures to exercise the checks card's red state and failed-name list.

**Diffs (`PullRequestDiff`, 3 entries: `PR_412`, `PR_440`, `PR_421`).** Each has 3-4 `FileDiff` entries with real-looking unified-diff patches (Go source, a test file, a JSON fixture, a docs page). Two file paths (`producer_throttle_controller_test.go` and `large_dag_with_conditional_branches_and_retries.json`, both under `services/scheduler/internal/...`) run past 80 characters specifically to overflow the diff view's 40-column file list (`_FILE_ROW_WIDTH` in `views/diff.py`) and exercise its marquee/ellipsis truncation.

**Pushed branches.** `PUSHED_BRANCHES` holds 5 `PushedBranch` entries across four repositories, all authored by `dokafor`, exercising `GitHubPushedBranches`'s card list.

## Verification

Every id referenced by an `IssueDetail`'s `parent`/`sub_issues`/`blocked_by`/`blocks`/`related`, and every `ProjectIssue` actually reachable in a project's rendered tree (via the real `issue_tree()` from `views/project_issues.py`), resolves to a `DETAILS` entry or a top-level `Issue`. Every top-level `Issue`, `Project`, and `PullRequest` (the only items a user can open) has a `DETAILS` entry, so `DemoIntegration.fetch_detail`'s `self.details[item.id]` lookup never raises `KeyError`. This was checked with a throwaway script (written, run, and deleted) that imported both modules and walked every reference; final counts were 21 Linear items / 37 Linear details and 12 GitHub items / 13 GitHub details, with no failures.
